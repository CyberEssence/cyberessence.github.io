# `physdump://` — как я заставил ядро Linux отдать мне свою память, не загружая ни одного модуля

> *«Человеческое сознание — всего лишь физический феномен, объясняемый циркуляцией электрических сигналов по синапсам. Смысл существования во плоти лишь в том, чтобы подтвердить твоё бытие.»*


Есть задача, которая раньше решалась двумя способами. Первый — **AVML**, читает `/proc/kcore` из user-space. Второй — **LiME**, грузит модуль ядра и высасывает физическую память напрямую. Оба — рабочие. Оба — со швами. AVML на современных ядрах получает только часть картинки. LiME требует пересобрать `.ko` под каждое ядро и подписать его (или отключить Secure Boot).

А потом появилась **LEMON** (DFRWS EU 2026).

> eBPF-программа умеет вызывать `bpf_probe_read_kernel()`. Значит, она умеет читать произвольную память ядра. А если знать `page_offset_base` — базу линейного отображения физики — то физический адрес становится виртуальным одной строчкой:

```
virt = phys + page_offset_base
```

Никакого модуля. Никакого `/proc/kcore`. Только верификатор eBPF, который — если правильно написать — пропустит тебя внутрь.

Так родился **`physdump`**. ~400 строк. C в ядре. Go в user-space. LiME-совместимый дамп на выходе. Volatility 3 читает его как родного.

## `//` Архитектура: три части, один ритуал

```
┌──────────┐  update req   ┌───────────┐  read page  ┌──────────┐
│   Go     │ ────────────► │ eBPF map  │ ◄────────── │  Ядро    │
│ userspace│               │ (request) │             │(phys mem)│
│          │  syscall      └───────────┘             └──────────┘
│          │ ──getpid──► tracepoint ─► eBPF-программа
│          │               ┌───────────┐
│          │ ◄── lookup ── │ eBPF map  │
│          │               │ (result)  │
└──────────┘               └───────────┘
```

Почему **`getpid()`**? Потому что это самый дешёвый и самый частый syscall в системе. Каждый процесс дёргает его сотни раз в секунду. Идеальный триггер — никто не заметит лишнего вызова среди моря таких же.

eBPF-программа фильтрует события по TGID. Она реагирует **только** на наш процесс. Система продолжает жить как ни в чём не бывало.

## `//` Шаг 1. eBPF: то, что живёт в ядре

Файл `bpf/phys_dump.bpf.c`. Никакого `vmlinux.h` — только базовые типы и helper'ы.

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

#define BLOCK_SIZE 4096
```

Две структуры. Одна — запрос. Другая — ответ. Обратите внимание на поле `seq`: без него user-space не поймёт, **чьё** это эхо — старое или новое.

```c
struct request {
    __u64 phys;
    __u64 seq;
    __u32 size;
    __u32 pad;
};

struct result {
    __u64 seq;
    __s32 status;
    __u32 size;
    __u8 data[BLOCK_SIZE];
};
```

Две map'ы. `BPF_MAP_TYPE_ARRAY`, по одному элементу. Это не изящно. Это работает.

```c
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, struct request);
} requests SEC(".maps");

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, struct result);
} results SEC(".maps");
```

Две глобальные переменные. Go-программа запишет их **до** загрузки объекта.

- `page_offset_symbol` — **адрес символа** `page_offset_base` (не его значение! это важно).
- `collector_tgid` — PID нашего процесса, чтобы фильтровать.

```c
const volatile __u64 page_offset_symbol = 0;
const volatile __u32 collector_tgid = 0;
```

И сама программа. Висит на tracepoint `sys_enter_getpid`. Срабатывает на каждый `getpid()`. Действует — только на наш.

```c
SEC("tracepoint/syscalls/sys_enter_getpid")
int dump_page(void *ctx)
{
    __u32 tgid = bpf_get_current_pid_tgid() >> 32;
    if (tgid != collector_tgid)
        return 0;

    __u32 key = 0;
    struct request *req = bpf_map_lookup_elem(&requests, &key);
    struct result *res = bpf_map_lookup_elem(&results, &key);
    if (!req || !res)
        return 0;

    __u64 seq = req->seq;
    __u64 phys = req->phys;
    __u32 size = req->size;

    if (!seq || res->seq == seq)
        return 0;

    res->size = 0;
    res->status = -22; /* EINVAL */

    if (!size || size > BLOCK_SIZE) {
        res->seq = seq;
        return 0;
    }
```

**Ключевой момент.** Мы знаем **адрес** символа `page_offset_base`, но нам нужно его **значение**. И мы читаем его тем же способом, каким будем читать физику:

```c
    __u64 base = 0;
    long rc = bpf_probe_read_kernel(
        &base, sizeof(base), (const void *)page_offset_symbol
    );
    if (rc) {
        res->status = (__s32)rc;
        res->seq = seq;
        return 0;
    }
```

Проверка на переполнение. И — само чтение.

```c
    if (!base || phys > (~(__u64)0 - base)) {
        res->status = -22;
        res->seq = seq;
        return 0;
    }

    __u64 virt = base + phys;
    rc = bpf_probe_read_kernel(res->data, size, (const void *)virt);

    res->status = (__s32)rc;
    if (!rc)
        res->size = size;

    res->seq = seq;
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

`bpf_probe_read_kernel()` — **единственный** легальный способ чтения произвольной памяти ядра из eBPF. Попытка разыменовать `(void *)virt` напрямую — мгновенный отказ верификатора. Helper существует именно для этого случая, и он разрешён.

Блок — 4096 байт. Ровно страница. Потому что helper имеет лимит на размер одного вызова (~8 КБ), и потому что страница — атомарная единица физической памяти.

### `parseIOMem` — карта мира

`/proc/iomem` — это физическая карта памяти. Нас интересуют строки с `System RAM`.

```go
func parseIOMem(path string) ([]memRange, uint64, error) {
    // ... открытие, чтение построчно ...
    for sc.Scan() {
        left, right, ok := strings.Cut(sc.Text(), ":")
        if !ok || strings.TrimSpace(right) != "System RAM" {
            continue
        }
        // ...
    }
```

Две частые аномалии, от которых нужно защититься. Первая: если `kptr_restrict` скрывает адреса — ядро отдаёт `0-0`. Вторая: некоторые ядра возвращают диапазон, заканчивающийся на `UINT64_MAX`, что сломает арифметику.

```go
        if start == 0 && end == 0 {
            return nil, 0, errors.New(
                "iomem addresses appear hidden: System RAM is 0-0",
            )
        }
        if end == math.MaxUint64 {
            return nil, 0, errors.New("unsupported RAM range ending at UINT64_MAX")
        }
```

Дальше — сортировка, проверка на пересечения, подсчёт общего объёма (пригодится для прогресса).

### `symbolAddress` — ищем точку входа

Формат `/proc/kallsyms`: `ffffffff82414320 D page_offset_base`. Третий столбец — то, что нам нужно.

```go
func symbolAddress(path, name string) (uint64, error) {
    // ...
    for sc.Scan() {
        fields := strings.Fields(sc.Text())
        if len(fields) < 3 || fields[2] != name {
            continue
        }
        addr, err := strconv.ParseUint(fields[0], 16, 64)
        if err != nil {
            return 0, err
        }
        if addr == 0 {
            return 0, fmt.Errorf("%s address is hidden or zero", name)
        }
        return addr, nil
    }
    // ...
}
```

Если адрес — ноль, значит ядро его прячет. Причины: `kptr_restrict=1`, `CONFIG_KALLSYMS_ALL=n`, lockdown в confidentiality. Тогда — мимо.

### `collector` — обёртка над ядром

```go
type collector struct {
    coll *ebpf.Collection
    hook link.Link
    req  *ebpf.Map
    res  *ebpf.Map
    seq  uint64
}
```

Создание. Первым делом — снять лимит memlock. Без этого загрузка eBPF может упасть с `EPERM`.

```go
func newCollector(object string, symbol uint64) (*collector, error) {
    if err := rlimit.RemoveMemlock(); err != nil {
        return nil, fmt.Errorf("memlock: %w", err)
    }

    spec, err := ebpf.LoadCollectionSpec(object)
    if err != nil {
        return nil, fmt.Errorf("read BPF object: %w", err)
    }
```

Глобальные переменные eBPF через `spec.Variables`. `Set` работает для `const volatile` в `.rodata`.

```go
    constants := map[string]interface{}{
        "page_offset_symbol": symbol,
        "collector_tgid":     uint32(os.Getpid()),
    }

    for name, value := range constants {
        variable, ok := spec.Variables[name]
        if !ok {
            return nil, fmt.Errorf(
                "BPF variable %q not found: rebuild the BPF object with -g",
                name,
            )
        }
        if err := variable.Set(value); err != nil {
            return nil, fmt.Errorf("set BPF variable %q: %w", name, err)
        }
    }
```

Привязка к tracepoint.

```go
    coll, err := ebpf.NewCollection(spec)
    // ...
    hook, err := link.Tracepoint(
        "syscalls", "sys_enter_getpid", prog, nil,
    )
    // ...
```

### `Read` — сердце

Метод вызывается для каждой страницы физической памяти. Кладёт запрос. Дёргает `getpid()`. Ждёт ответа.

```go
func (c *collector) Read(phys uint64, size uint32) ([]byte, error) {
    if size == 0 || size > blockSize {
        return nil, errors.New("invalid read size")
    }
    if c.seq == math.MaxUint64 {
        return nil, errors.New("request sequence overflow")
    }
    c.seq++

    key := uint32(0)
    req := request{
        Phys: phys,
        Seq:  c.seq,
        Size: size,
    }
    if err := c.req.Update(&key, &req, ebpf.UpdateAny); err != nil {
        return nil, fmt.Errorf("update request: %w", err)
    }
```

**Осторожно.** Нельзя использовать `syscall.Getpid()`. В современных версиях Go обёртка кэширует результат — реального syscall'а не происходит, tracepoint не срабатывает. Нужен **raw** вызов:

```go
    _, _, errno := unix.RawSyscall(unix.SYS_GETPID, 0, 0, 0)
    if errno != 0 {
        return nil, fmt.Errorf("getpid trigger: %w", errno)
    }
```

А теперь — то, о чём не пишут в туториалах по eBPF. На **обычном ядре** tracepoint выполняется синхронно: syscall вернулся — программа уже отработала. Но на **PREEMPT_RT** обработчик может быть вытеснен и выполнен **отложенно**. User-space успевает прочитать map раньше, чем eBPF туда что-то положит. Поэтому — цикл ожидания с дедлайном:

```go
    var res result
    deadline := time.Now().Add(2 * time.Second)
    for {
        if err := c.res.Lookup(&key, &res); err != nil {
            return nil, fmt.Errorf("lookup result: %w", err)
        }
        if res.Seq == req.Seq {
            break
        }
        if time.Now().After(deadline) {
            return nil, fmt.Errorf(
                "BPF request timeout after 2s: got sequence %d, want %d",
                res.Seq, req.Seq,
            )
        }
        runtime.Gosched()
    }
```

`runtime.Gosched()` не даёт забить CPU busy-wait'ом. `2s` — защита от вечного ступора, если eBPF-программа почему-то не сработает.

Проверка ответа и — возврат:

```go
    if res.Status != 0 {
        return nil, fmt.Errorf(
            "physical read at %#x: BPF status %d",
            phys, res.Status,
        )
    }
    if res.Size != size {
        return nil, fmt.Errorf(
            "unexpected result size: got %d, want %d", res.Size, size,
        )
    }

    return res.Data[:int(size)], nil
}
```

### `run` — весь танец целиком

```go
func run() (retErr error) {
    outPath := flag.String("out", "", "output LiME file")
    object := flag.String("bpf", "bpf/phys_dump.bpf.o", "BPF object")
    flag.Parse()

    if *outPath == "" {
        return errors.New("usage: sudo ./physdump -out /mnt/evidence/ram.lime")
    }
    if os.Geteuid() != 0 {
        return errors.New("run as root; kernel security policy may still deny access")
    }
```

Дальше — контекст с ловлей `SIGINT`. `Ctrl+C` должен останавливать дамп **между страницами**, а не рвать файл на полу.

```go
    ctx, stop := signal.NotifyContext(
        context.Background(), os.Interrupt, syscall.SIGTERM,
    )
    defer stop()
```

Читаем карту, ищем символ, поднимаем collector.

```go
    ranges, total, err := parseIOMem("/proc/iomem")
    // ...
    symbol, err := symbolAddress("/proc/kallsyms", "page_offset_base")
    // ...
    c, err := newCollector(*object, symbol)
    // ...
    defer c.Close()
```

**Preflight-чтение.** Читаем первую страницу первого диапазона **до** создания выходного файла. Если механизм не работает — не создаём мусор.

```go
    firstSize := uint64(blockSize)
    if n := ranges[0].End - ranges[0].Start + 1; n < firstSize {
        firstSize = n
    }
    if _, err := c.Read(ranges[0].Start, uint32(firstSize)); err != nil {
        return fmt.Errorf("preflight read: %w", err)
    }
```

Пишем в `*.partial`, в конце — `RENAME_NOREPLACE`. Атомарно. Если что-то рухнет — останется `.partial`, а не битый `ram.lime`.

```go
    partial := *outPath + ".partial"
    out, err := os.OpenFile(
        partial, os.O_WRONLY|os.O_CREATE|os.O_EXCL, 0600,
    )
    if err != nil {
        return err
    }
```

Основной цикл. Для каждого диапазона — LiME-заголовок, потом страницы.

```go
    var done uint64
    for _, r := range ranges {
        fmt.Printf("Reading %#x-%#x\n", r.Start, r.End)

        h := limeHeader{
            Magic:   limeMagic,
            Version: 1,
            Start:   r.Start,
            End:     r.End,
        }
        if err := binary.Write(out, binary.LittleEndian, &h); err != nil {
            return err
        }

        for phys := r.Start; phys <= r.End; {
            if err := ctx.Err(); err != nil {
                return err
            }

            n := uint64(blockSize)
            if remaining := r.End - phys + 1; remaining < n {
                n = remaining
            }

            data, err := c.Read(phys, uint32(n))
            if err != nil {
                return err
            }
            if err := writeAll(out, data); err != nil {
                return err
            }

            phys += n
            done += n
        }
    }
```

Финал: `fsync`, `close`, переименование.

```go
    if err := out.Sync(); err != nil {
        return err
    }
    err = out.Close()
    closed = true
    if err != nil {
        return err
    }

    if err := unix.Renameat2(
        unix.AT_FDCWD, partial,
        unix.AT_FDCWD, *outPath,
        unix.RENAME_NOREPLACE,
    ); err != nil {
        return fmt.Errorf("publish output: %w", err)
    }
```

`main` — просто обработка ошибок. Отдельно распаковывается `*ebpf.VerifierError`: если верификатор забраковал — полезно увидеть полный вывод.

```go
func main() {
    if err := run(); err != nil {
        var verifierErr *ebpf.VerifierError
        if errors.As(err, &verifierErr) {
            fmt.Fprintf(os.Stderr, "Verifier:\n%+v\n", verifierErr)
        }
        fmt.Fprintln(os.Stderr, "Error:", err)
        os.Exit(1)
    }
}
```

```makefile

	-O2 -g -Wall -Werror

.PHONY: all clean

all: physdump

bpf/phys_dump.bpf.o: bpf/phys_dump.bpf.c

physdump: main.go go.mod bpf/phys_dump.bpf.o
```

`-g` — **обязательно**. Без отладочной информации `cilium/ebpf` не найдёт переменные `page_offset_symbol` и `collector_tgid` в `.rodata`.

## `//` Шаг 5. Volatility 3: восстановление воспоминаний

```bash
sudo apt install -y git python3-pip python3-venv build-essential

git clone https://github.com/volatilityfoundation/volatility3.git
cd volatility3
python3 -m venv env
source env/bin/activate
pip install --upgrade pip
pip install -e ".[full]"
```

Volatility 3 не понимает структуры ядра сам по себе. Ему нужен **ISF** — Intermediate Symbol File. Генерируется из `vmlinux` с отладочной информацией через `dwarf2json`.

```bash
uname -r
# 6.1.0-53-amd64

sudo apt install -y linux-image-$(uname -r)-dbg
ls /usr/lib/debug/boot/vmlinux-$(uname -r)
```

`dwarf2json` требует 8–16 ГБ RAM. Иначе — `Killed` от OOM.

```bash
git clone https://github.com/volatilityfoundation/dwarf2json.git
cd dwarf2json
go build

./dwarf2json linux \
    --elf /usr/lib/debug/boot/vmlinux-$(uname -r) \
    > ~/linux-$(uname -r).json

mkdir -p ~/volatility3/volatility3/framework/symbols/linux
cp ~/linux-$(uname -r).json \
```

## `//` Подводные камни: то, что я узнал исходя из своего исследования

### 1. `/proc/kcore` — не так прост, как кажется

Первый соблазн — скопировать `/proc/kcore`. Не сработает. Это **ELF-образ** ядра с виртуальными адресами. Volatility его не примет как LiME.

### 2. Размер блока в `bpf_probe_read_kernel()`

Блоки по 2 МБ → ошибка:

```
Error: BPF request not completed: got sequence 473361, want 473366
```

Две причины. Первая: helper имеет лимит на один вызов (~8 КБ). Вторая: на **PREEMPT_RT** tracepoint может выполняться отложенно. User-space возвращается из syscall'а раньше, чем eBPF-программа что-то запишет в map.

Решение — читать по одной странице (4 КБ) и **polling** в `Read`. Именно поэтому в импортах Go появились `runtime` и `time`.

### 3. `dwarf2json` и OOM-killer

Если в VM 2 ГБ RAM — `dwarf2json` будет убит молча. `Killed`. Без stack trace.

Варианты:
- Поднять RAM до 16 ГБ.
- Большой swap (медленно).
- `zram` — сжатый swap в RAM.

### 4. Несовпадение версии ядра и ISF

Генерировать ISF только **под ту же версию**, что в баннере.

### 5. Права на выходной файл

`physdump` под `sudo` создаёт `ram.lime` с владельцем `root:root` и `0600`. Обычный пользователь не прочитает. Volatility упадёт с `Permission denied`.

```bash
sudo chown $USER:$USER ram.lime
sudo chmod 644 ram.lime
```

### 6. `cilium/ebpf` требует Go 1.21+

Просто поставь golang более новой версии :)

### 7. `linux-tools-$(uname -r)` может не найтись

На RT-ядрах Debian пакета часто нет. И это **не проблема**. `physdump` не зависит от `perf` или `bpftool`. Достаточно `clang`, `libbpf-dev` и `linux-headers-$(uname -r)`. Убери `linux-tools` из списка — остальное установится.

## `//` Что в итоге

~400 строк. C в ядре. Go в user-space. LiME-совместимый дамп. Volatility 3 читает как родного.

eBPF даёт три вещи, которых не дают ни LiME, ни AVML:

- **Модуль не нужен.** Работает в песочнице верификатора. Ничего не грузим — ничего не подписываем.
- **CO-RE.** Один `.o` для разных ядер. При наличии BTF — не пересобирать.
- **Скриптуется.** Go-обвязка легко расширяется: сеть, сжатие, параллельная запись.

Ограничения тоже есть. Нужен **root**. Нужен доступ к `/proc/kallsyms`. **RT-ядра** требуют polling. Для форензики в контролируемой среде — этого хватает.
